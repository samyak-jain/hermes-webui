# Vegapunk WebUI architecture note

## Identity and source

This dashboard is **Hermes WebUI**, not the dashboard shipped in the Hermes
Agent repository. Its source is the `samyak-jain/hermes-webui` fork of
`nesquena/hermes-webui`. Kumo currently deploys the `v0.52.41` maintenance
line with local EFS/SQLite backports; the deployed image is pinned by digest in
`kumo:tofu/variables.tf:96`.

The application deliberately has no frontend framework, bundler, or build
step. It is a Python standard-library threaded HTTP server plus HTML, CSS, and
vanilla JavaScript (`README.md:534`, `server.py:118`). HTTP authentication and
route dispatch enter through `server.py:375`; most routes live in
`api/routes.py`, and the browser code lives under `static/`.

## Authentication and exposure on Kumo

The public URL is `https://webui.samyak.dev/`. Cloudflare DNS points it at the
outbound Cloudflare Tunnel, and a Cloudflare Access self-hosted application
allows the configured operator email through email OTP
(`kumo:tofu/cloudflare.tf:64`, `kumo:tofu/cloudflare.tf:73`,
`kumo:tofu/cloudflare.tf:92`).

The container listens on `0.0.0.0:8787`, but Podman publishes it only as host
`127.0.0.1:8787` (`kumo:nix/modules/hermes-webui.nix:13`). Cloudflare
terminates TLS and forwards to that loopback listener. The deployed
`v0.52.41` image does not enforce trusted-header identity itself, so
Cloudflare Access is the effective authentication boundary; the
`Cf-Access-Authenticated-User-Email` settings are forward-compatible for a
newer WebUI (`kumo:nix/modules/hermes-webui.nix:52`).

WebUI also supports its own optional password/cookie authentication, but Kumo
does not enable it. The request middleware still passes every request through
`check_auth` (`server.py:375`).

## Hermes gateway, agent source, and durable state

WebUI runs a Hermes agent **in process**. Ordinary chat does not proxy through
the separately running Hermes gateway (`README.md:151`). Kumo mounts the
gateway's EFS-backed Hermes home from host `/mnt/efs/hermes` to container
`/opt/data` and sets `HERMES_HOME=/opt/data`
(`kumo:nix/modules/hermes-webui.nix:18`, `kumo:nix/modules/hermes-webui.nix:33`).
Consequently the WebUI can directly read the same config, sessions, skills,
memory, credentials, and databases as the gateway.

The matching Hermes Agent source is refreshed from the pinned agent image into
the host-managed `kumo-hermes-agent-src` volume, then mounted read-only at
`/opt/hermes` (`kumo:nix/modules/hermes-webui.nix:28`,
`kumo:nix/modules/hermes-webui.nix:96`). The container entrypoint installs the
agent package and dependencies from that source (`docker_init.bash:405`).

`HERMES_API_URL=http://10.89.10.10:8642` reaches the gateway container over
the private `kumo-hermes` Podman network
(`kumo:nix/modules/hermes-webui.nix:46`). In the default runtime it is used for
gateway health/status probing, especially the Tasks/cron status surface
(`api/agent_health.py:337`, `api/agent_health.py:568`); it is not the Kanban
data path and does not route ordinary chat.

## Kanban data path

The initial board render is owned by `loadKanban()` in
`static/panels.js:2667`. It resolves board metadata/config, fetches
`/api/kanban/board`, updates filters/statistics, renders the board, and starts
the SSE event subscription. Kanban routes are dispatched from
`api/routes.py:11930` into `api/kanban_bridge.py`.

The bridge lazily imports `hermes_cli.kanban_db` from the mounted Agent source
(`api/kanban_bridge.py:28`). It opens a short-lived SQLite connection per
request and closes it at the request boundary (`api/kanban_bridge.py:82`).
Connection creation owns one-time schema initialization; callers must not
force `init_db()` on every read because that API intentionally invalidates the
Agent library's initialized-path cache and reruns integrity/migration work.
The board query, dependency/comment counts, and statistics share one
connection (`api/kanban_bridge.py:215`).

On Kumo the default-board database resolves to container
`/opt/data/kanban.db`, therefore host `/mnt/efs/hermes/kanban.db`. It is on
EFS/NFS, not local block storage. Kumo injects the same EFS-safe SQLite policy
used by the gateway through `/etc/hermes/config.yaml`
(`kumo:nix/modules/hermes-webui.nix:24`). Network-filesystem round trips are
therefore unusually expensive; keep board loads bounded in request count and
never re-run schema/integrity initialization in a steady-state read.

The regression envelope is documented in `TESTING.md`: a warm load stays at
three HTTP requests in two waves with no forced `init_db()`, the 500-task
CPU-side fixture must remain below 500 ms p95, and an isolated EFS-equivalent
500-task benchmark must remain below 750 ms p95 for the board endpoint and
1.5 s p95 for the two-wave API critical path. The fixture uses 25 assignees and
10 tenants, measures 20 loads after one warm-up, and keeps cold process
initialization separate.

## Build and deployment

`Dockerfile` copies the repository to `/apptoo`, bakes the tag into
`api/_version.py`, exposes port 8787, and runs `docker_init.bash`
(`Dockerfile:89`, `Dockerfile:95`, `Dockerfile:98`, `Dockerfile:107`).
The entrypoint aligns the runtime UID/GID with the mounted data, seeds writable
`/app` from image-owned `/apptoo`, creates/reuses `/app/venv`, installs the
WebUI and mounted-agent dependencies, drops privileges, and runs
`python server.py` (`docker_init.bash:290`, `docker_init.bash:313`,
`docker_init.bash:369`, `docker_init.bash:490`).

Pushing a `v*` tag runs `.github/workflows/release.yml`: it creates a GitHub
release and builds/pushes multi-architecture `amd64` and `arm64` images to
GHCR (`.github/workflows/release.yml:3`, `.github/workflows/release.yml:46`).
The full git ref (for example `v0.52.41-kumo.5`) is the primary image tag and
the `org.opencontainers.image.version` label; the base `0.52.41` and `latest`
tags remain compatibility aliases.
Kumo pins the resulting digest rather than a mutable tag, and Nix owns the
`podman-hermes-webui.service` container declaration and ordering
(`kumo:nix/modules/hermes-webui.nix:85`).

To ship a change: merge it into the Kumo maintenance branch, create the next
maintenance tag, wait for the multi-arch image, update the digest in
`kumo:tofu/variables.tf`, and deliver that Kumo pin through its normal PR and
deployment workflow. Replacing `podman-hermes-webui.service` restarts only the
WebUI container; do not restart `podman-hermes.service` merely to update this
UI.

## Running locally

Use an isolated Hermes home unless intentionally testing real agent state:

```sh
git clone https://github.com/samyak-jain/hermes-webui.git
cd hermes-webui
HERMES_HOME=/tmp/hermes-webui-agent-home \
HERMES_WEBUI_STATE_DIR=/tmp/hermes-webui-state \
HERMES_WEBUI_AGENT_DIR=/path/to/hermes-agent \
HERMES_WEBUI_PORT=8789 \
python3 bootstrap.py --no-browser
```

The normal entry points are `python3 bootstrap.py`, `./start.sh`, or
`./ctl.sh start` (`README.md:113`). Host and port overrides are documented at
`README.md:353`. Run tests through `./scripts/test.sh`, not bare pytest; the
wrapper selects a supported Python and installs the development dependencies.
